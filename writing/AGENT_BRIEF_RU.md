# Задание агенту по проверке четырёх складских ограничений

Начни с этого файла. Цель - установить, сколько раз в завершённой серии модель действительно нарушила каждое из четырёх ограничений, и уточнить вывод по H2. Выражение «четыре случая» обозначает четыре типа потенциальных нарушений. Четыре инцидента в эксперименте никто не обнаруживал.

## Почему требуется проверка

В замороженной версии `series_py312/src/simulator.py`, метод `Simulation.metrics()`, строка 435, поля `duplicate_receipts`, `illegal_moves`, `illegal_release` и `negative_stock` получают буквальное значение 0. В `scripts/build_report.py`, функция `compare()`, проверка H2 суммирует эти поля для варианта C в S1/L2. Поэтому нули из CSV нельзя использовать как независимый подсчёт. В коде есть проверки переходов и балансов, а на реальной Odoo выполнены интеграционные тесты. Эти свидетельства сохраняют значение в пределах своего охвата.

Первичный эффект H2 измерен отдельно. При парном сравнении B и C в S1/L2 ограниченное время до первичного размещения сократилось в среднем на 7,90 с, интервал 97,5% от 5,20 до 11,04 с. Верхняя граница интервала для роста просрочки подготовки равна 0,79 п.п. при пределе 1 п.п. Открыт вопрос о складских нарушениях. Основание для чисел - `series_py312/artifacts/hypotheses.json`, ключ `hypotheses.H2`.

## Что искать

| Поле | Как распознать нарушение | Пример, который должен пройти проверку |
|---|---|---|
| `duplicate_receipts` - повторная приёмка | Для одной пары run_id и pallet состоялось второе успешное событие `register`. Считать каждое лишнее проведение после первого. В Odoo сверить число приходных документов и прирост остатка. | Повтор MQTT-сообщения, `idempotent_duplicate` или второй ответ с тем же ID проводки при единственном оприходовании. |
| `illegal_moves` - недопустимое перемещение | Проверить состояние и право на адрес в момент `reserve_and_start`, затем тот же резерв и паллету при `physical_move_end` и `confirm_place`. Учесть чужой или уже занятый адрес, несовместимую товарную группу, обычную зону при блокировке качества, перемещение до приёмки. | Размещение удержанной паллеты в карантине, затем отдельный рейс в обычную зону после выпуска. |
| `illegal_release` - неправомерное снятие блокировки качества | Восстановить начальный статус и историю разрешений. Переход удержанной паллеты в released требует внешнего разрешения. В Odoo проверить роль, действие и изменение состояния. Незаконное размещение при неизменном hold относится к предыдущей строке. | Паллета с исходным разрешением, штатное `external_release` или отклонённый запрос от роли ТСД, после которого статус сохранился. Само имя события в SimPy не удостоверяет полномочия пользователя Odoo. |
| `negative_stock` - отрицательный остаток | Восстановить начальный запас и после каждого проведённого движения проверять остатки источника и назначения по доступным ключам. Для физической модели вести отдельно паллеты в буфере, в пути и на адресах. Зафиксировать первый переход баланса ниже нуля. | `unfilled_outbound` при отсутствии товара не списывает запас. Успешное выбытие начального запаса может иметь пустой идентификатор входящей паллеты. |

## Порядок независимой проверки

1. Возьми `series_py312/artifacts/simulation_freeze.json`, `run_manifest.csv` из той же папки и индивидуальный `runs/<run_id>/manifest.json`. Сверь fingerprint и хеши используемых файлов. Экономические таблицы и отчёт предыдущего агента не являются журналами движений.
2. Начни с пары `S1-L2-1000-B` и `S1-L2-1000-C`. Сохраняй порядок записей в `events.jsonl.gz`, в том числе при равных временных метках. Для каждой паллеты веди статус приёмки, статус качества, резерв и размещение. Для склада веди владельца места и баланс. Начальную занятость и SKU восстанови по инициализации замороженного симулятора для данного сценария и seed. Склад уже заполнен к началу прогрева. Обрабатывай также прогрев и завершающие сутки.
3. Проверь сам анализатор на копиях коротких трасс. По очереди добавь повтор `register`, подмени адрес на занятый, смоделируй изменение качества без разрешения, повтори расход из исчерпанного источника. Рядом дай корректные контрольные примеры из таблицы. Отдельно обозначь, какую ошибку обнаруживает анализатор и какое свидетельство для этого требуется. Инъекции относятся только к его тестам.
4. Для вывода о H2 охвати все 20 пар B/C в S1/L2. Полные журналы сохранены для seed 1000 во всех 54 ячейках. Для остальных seed восстанови поток событий из замороженной версии с подробным логированием. Пример воспроизведения - `scripts/verify_reproduction.py`, в исходном виде он проверяет только S1/L1/C. Сверь входы и метрики каждой восстановленной реализации с манифестом. Если заявляешь результат по всей серии, проверь все 1080 запусков и укажи фактический охват.
5. Где журнал не содержит начального состояния, автора операции или отдельной проводки, укажи «недостаточно данных» и требуемое поле. Когда нужен дополнительный журнал, создай отдельно инструментированную копию и проверь совпадение исходных переходов и метрик. Отделяй модель от Odoo: свидетельства реального ПО находятся в `artifacts/integration_results.json`, `artifacts/api_concurrency.json` и `artifacts/replay/`. Выборка Odoo содержит реальные проводки выбранных паллет при восстановленной фоновой занятости.
6. Верни таблицу «тип проверки / проверенные запуски и операции / нарушений / первый пример / источник / ограничения». Для примера укажи run_id, pallet, время, состояние до и после, строку журнала или ID документа. Отдельно вынеси вердикт по защитному условию H2 и готовую формулировку для статьи. Нулевой результат допустим при проверяемом охвате, а непроверенные операции указывай отдельно. Изменения храни отдельно от исходной серии.

## Какой архив использовать

Компактный архив содержит статью, сводные результаты, код и полные трассы одной пары B/C. Его достаточно для разбора постановки и разработки анализатора. Полный архив содержит также остальные сохранённые журналы, компактные результаты по всем запускам, данные и модели для воспроизведения. В обоих архивах точка входа в статью - `writing/article.md`.
