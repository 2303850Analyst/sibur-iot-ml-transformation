# ОБЯЗАТЕЛЬНЫЙ SETUP ПЕРЕД НОЧНОЙ СЕРИЕЙ V3.1

> Назначение: настроить текущий Windows 11/10 + WSL2 + Docker Desktop + Python стенд под Intel i5-14400F (6P+4E, 16 потоков), 32 GB RAM, Samsung 990 Pro NVMe (1 TB свободно), RTX 3060 12 GB. **Никаких действий, изменяющих V1/V2, результаты, физику модели или экспериментальный протокол.** Настройки являются стартовыми ресурсными ориентирами и должны подтверждаться измерениями. Не объявляй setup выполненным, пока не зафиксированы результаты проверок.

## A. Инвентаризация и безопасность (перед любыми изменениями)

1. Определи точные пути к проекту и Docker Compose из существующего репозитория — не создавай новый стек, если текущий уже существует. Сними `git status`, commit, контрольные суммы протокола, текущие `docker compose ps`, `docker compose config`, `docker info`, `docker system df -v`, `docker images`, `docker stats --no-stream`, `wsl -l -v`, а также CPU/RAM/свободный SSD. Сохрани исходный Docker Compose и `.wslconfig` в безопасные резервные копии. Зафиксируй image digests, имена и размеры томов; не предполагай, что один образ = весь стек.
2. Запрещено выполнять `docker system prune`, `docker volume prune`, `docker compose down -v`, удалять/пересоздавать тома с V1/V2 либо менять исходную БД без проверенного backup/rollback. Предыдущие образы, V1/V2, пилоты и checkpoint не удалять ради освобождения места. Не делать незапрошенную переустановку Docker, WSL или драйверов.
3. Сохрани `environment_before.json` с CPU, логическими процессорами, WSL RAM, swap, Docker-версией, Compose-конфигурацией, контейнерами, image/volume disk usage и реальным свободным пространством. Невозможность прочитать метрику — явно укажи UNKNOWN.

## B. Windows + WSL2 — предложить и применить только безопасно

**Рекомендуемый стартовый лимит** файла `%USERPROFILE%\.wslconfig`:

```ini
[wsl2]
memory=22GB
processors=12
swap=4GB
```

Уже существующий `.wslconfig` изменяй минимальным diff с сохранением остальных нужных настроек. Проверяй, что Docker Desktop использует WSL2 backend. Приоритет — не ломать действующий стенд и не расходовать всю RAM Windows. Перед применением требуется отсутствие критически работающих контейнеров/задач. `wsl --shutdown` и последующий запуск Docker Desktop останавливают WSL-контейнеры; выполнять только после сохранения checkpoint и подтверждения разрешения на остановку. Если безопасное изменение невозможно, оставь текущие параметры, укажи причину и адаптируй число воркеров.

Перед ночным запуском проверь Windows sleep/hibernate (при питании от сети). Если пользователь разрешил изменение:

```powershell
powercfg /change standby-timeout-ac 0
powercfg /change hibernate-timeout-ac 0
```

Выключение монитора допустимо. Не меняй политики обновлений или безопасность Windows без разрешения; проверь, не запланирована ли перезагрузка. При запрете изменения настроек подготовь точные инструкции пользователю и не выдавай их за выполненные действия.

## C. Docker Compose и выделение ресурсов

1. Используй текущие версии Odoo 19, PostgreSQL, Mosquitto, аддонов и шлюза — заморозь версии и image digests до основной серии. Не меняй их между масками. `docker compose config` должен успешно валидироваться. Все контейнеры должны быть `healthy` (если healthcheck предусмотрен), БД доступна, MQTT принимает и подтверждает тестовое событие; восстановление и rollback испытаны на изолированном тестовом снимке.
2. **Стартовый бюджет одной Odoo-копии**: Odoo 3–5 GB RAM, PostgreSQL 1–2 GB, Mosquitto менее 0,25 GB, генератор 20 пользователей 0,5–1 GB, плюс файловые кэши и WSL. Это не установленный фактический RSS и не команда ставить жёсткие `mem_limit`: перед лимитами и числом workers измерь пик. Если применены лимиты, одинаково заморозь их для всех сравниваемых масок и зафиксируй в manifest. OOM и swap — причина остановки/снижения параллельности, не основание выкидывать тяжёлые маски.
3. Для интеграционного replay B два стека разрешены **только при** независимых PostgreSQL БД/томах, MQTT namespace или брокерах/темах, портах, очередях и учетных данных. Используй отдельные Compose project names, не дублируй общий production volume. Оба стека на идентичных версии, конфигурации, снимке данных. Если второй стек ухудшает throughput, оставь один.
4. Для длительной нагрузки C — **строго один** Odoo-стек и 20 одновременно активных пользователей в измеряемом окне, без запуска CPU-heavy SimPy и второго стресс-окна на том же хосте. Одновременность пользователей должна подтверждаться журналом действий, не только числом логинов. Характеристики контейнера, `workers`, `db_maxconn`, память и CPU не менять между сравниваемыми окнами.

## D. Симулятор SimPy / Python и SSD

1. Запускай A через независимые `multiprocessing` процессы: начальная точка — 6, сравни 4/6/8 на одинаковых входах. Выбери 8 только если реально быстрее и не вызывает OOM/swap/троттлинг. Один процесс ≠ одна паллета; каждый независимо исполняет полный 25-операционный процесс и все правила блокировок.
2. Установи **до импорта numpy/scikit-learn** для дочерних процессов `OMP_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1`, `MKL_NUM_THREADS=1`, `NUMEXPR_NUM_THREADS=1`. Избегай вложенных параллельных пулов и ненужного GPU. ML-модели train/test фиксированы; кэширование не должно раскрывать будущее.
3. Горячие данные, Docker volumes и результаты интенсивной записи размещай в файловой системе Linux WSL2 на NVMe (например, `~/wms_inbound_experiment`), не в `/mnt/c` при миллионах малых I/O. Не переносить активную БД грубым копированием файлов. Сохраняй компактные агрегаты на каждый из 46 080 запусков; полные трассы — только заранее выбранные контрольные + аномалии. Для каждого запуска сохраняй seed, manifest hash, код, KPI, статус аудита; детальное журналирование не заменяй без аудита воспроизводимости.
4. Дисковый preflight: определить реальный размер Docker images, volumes, WSL VHDX и свободное место; держать резерв не менее 100 GB, предупредить при достижении 150 GB свободного места. Нельзя автоматически освобождать место удалением проектных данных. Сохранять результаты атомарно и с checkpoint/resume.

## E. Автоконтроль и разрешение на основную серию

1. Замерь `docker stats`, RSS Python, swap, CPU, SSD во время preflight 4/6/8. Сохрани p50/p95 времени, память и скорость для тяжёлых S4/L2, S5/L2, S6/L3. Если свободная RAM опускается ниже 3 GB, swap интенсивно растёт, Docker OOM, перегрев/троттлинг — уменьши число исполнителей и отметь в отчёте.
2. Заморозь выбор числа процессов/стеков и ресурсные лимиты до основной серии A/B/C. Допустимая вынужденная деградация числа воркеров фиксируется как изменение *исполнителя*, а не бизнес-параметров; для сравнения времен Odoo при смене оборудования/ресурсов серия признаётся отдельной или перезапускается сопоставимым образом.
3. Создай `experiment_v3/report/ENVIRONMENT_SETUP_RU.md`, `environment_before.json`, `environment_after.json`, снимок `docker compose config`, перечень проверок и их PASS/FAIL/UNKNOWN. Только после успешного preflight и сохранённых checkpoint запускай полную серию. Предпочтительно сначала A, затем B; C только на свободном, неизменном стенде.

## Примечание об одинаковых условиях

Объём ресурсов для **всех конфигураций в рамках одного испытательного контура одинаков**. Ускорение от изменения конфигурации ПК, Docker лимитов или числа рабочих процессов не является эффектом WMS/IoT/ML. Стресс-время HTTP и модельное время складской приёмки никогда не сравниваются как одна метрика.
