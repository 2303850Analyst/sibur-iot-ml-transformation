**Статус:** спецификация и зафиксированная *предлагаемая* параметризация ДО первой основной серии. Дата сборки: 20.11.2026. **Никакие 46 080 основных симуляций здесь не выполнены.**

**Один файл — полный промпт.** Его поддерживают копии исходных файлов и проверочные инструменты внутри ZIP. Рабочий проект на ПК пользователя: `wms_inbound_experiment`. Сохрани исходные V1/V2 и технический пилот V3. Для прежнего технического пилота S1/L1 число 82,34 минуты относится к ДРУГОЙ параметризации, не переносить его в новую серию V3.2.

## A0. ПРИОРИТЕТ И НЕДОПУСТИМЫЕ СОКРАЩЕНИЯ

1. **Этот раздел и последующие A1–A7 имеют приоритет над встроенной ниже полной спецификацией V3.1** в любом расхождении. Базовый документ V3.1 подчинён новым правилам V3.2 по времени, ресурсам, журналированию и техническому окружению.
2. **Обязательные испытания не сокращать:** контур A = 128 бинарных масок × 6 сценариев × 3 нагрузки × 20 семян = **46 080 сквозных прогонов**; B = 128 × 6 × 3 × 3 = **6 912 событийных replay в реальной Odoo 19**; C = 25 заранее зафиксированных масок × 6 × 3 × 3 = **1 350 настоящих стресс-окон** (60 с активных + 15 с хвоста; 20 пользовательских сессий в каждом). B не называется непрерывным стрессом. C не расширяется на все 128 масок.
3. **Заморозь `ASIS_BASELINE_PARAMETER_FREEZE.json` и правила превращения модулей в действия ДО запуска основной серии.** AS-IS всегда WMS+ТСД, без складского IoT и ML; цифры — явно помеченные сценарные предположения, НЕ замеры предприятия. После просмотра эффектов C127 менять параметры запрещено. Любая исправленная параметризация — новая, отдельно сопоставимая серия с полным повтором равных масок.
4. **Не назначать целевой полный цикл и проценты эффективности.** TO-BE получает только изменение реального составного действия, частоты исключений, разрешённых маршрутов, времени подтверждений и очередей. Не заменять 90 с человеческой работы одним 0,3 с API; автоматические системные транзакции и сохранившиеся обязательные проверки учитываются раздельно.
5. **УЧЁТ ПО КАЖДОМУ ЗАПУСКУ:** для каждого `(mask,S,L,seed)` сохранять все входные хеши, версию кода, полные KPI и самостоятельный статус аудита. **ПО КАЖДОМУ ПОСТУПЛЕНИЮ:** `case_id`, готовность, все временные отметки закрытия, фактический исход, T72, все 25 векторов операций P01–P25 (визиты, занятость людей по ролям, техника, очереди по причинам, пропуски условных ветвей, вклад в критический путь). Нет агрегата вместо каждого поступления. Детальные визиты по предзаданной диагностической выборке; любой отдельный случай ДОЛЖЕН детерминированно воспроизводиться до уровня визита, с проверкой контрольных сумм. Если replay не точен — основной запуск не разрешён до исправления или организации полного персистентного лога.
6. **Ресурсный учёт:** во время P10/P18 одновременно заняты один водитель и один погрузчик; стоимость водителя и погрузчика не удваивать. Учёт рабочего времени в минутах не равен календарным минутам полного цикла и не смешивается с 20 параллельными HTTP-сессиями.
7. **Приоритет выполнения ночью:** preflight → полная серия A → полный B → последовательная серия C только на свободном стенде. Не создавать GPU-нагрузки и не запускать одновременно независимые стресс-окна Odoo на одном CPU. Сохранять checkpoint/resume и точный статус PARTIAL, если времени на ночь не хватит.
8. Не использовать старые пилоты как данные новой серии, не удалять Docker volumes и исходные результаты, не объявлять 1–10 пилотных пар статистическим доказательством пользы модулей.

## A1. КОНКРЕТНОЕ ЖЕЛЕЗО, НАСТРОЙКА WINDOWS + WSL2 + DOCKER

Компьютер: **Intel i5-14400F (6P+4E, 16 потоков), RAM 32 ГБ, Samsung 990 Pro NVMe (свободно около 1 ТБ), RTX 3060 12 ГБ.** Видеокарта для этого эксперимента не требуется. Основной ограничитель — CPU и файловый I/O больших данных.

**Обязательная инвентаризация (сохрани stdout/JSON):**

```powershell
wsl --list --verbose
docker info
docker compose ps
docker compose config
docker system df -v
docker stats --no-stream
docker images
Get-CimInstance Win32_Processor | Select-Object Name,NumberOfCores,NumberOfLogicalProcessors
Get-CimInstance Win32_ComputerSystem | Select-Object TotalPhysicalMemory
Get-Volume | Select-Object DriveLetter,SizeRemaining,Size
```

**Стартовая конфигурация `%USERPROFILE%\.wslconfig`**, только после безопасной диагностики и сохранения предыдущего файла:

```ini
[wsl2]
memory=22GB
processors=12
swap=4GB
```

Проверить WSL2 backend. `wsl --shutdown` может остановить существующие контейнеры; требуется сохранённый checkpoint и разрешение на остановку, не выполнять безусловно. Не менять настройки ОС, автоматически отключающие обновления/защиту. Перед ночной серией убедиться, что Windows не уходит в сон, проверить плановую перезагрузку. `powercfg /change standby-timeout-ac 0` и `powercfg /change hibernate-timeout-ac 0` — только после разрешения пользователя. **Это инструкция, не утверждение, что настройки уже выполнены.**

Docker Compose: исходный стек Odoo 19 + PostgreSQL + MQTT + интеграционный шлюз, **не переустанавливать и не уничтожать тома**. Снять image digests/версии, размеры томов и состояние здоровья; хранить результаты/активные данные в Linux FS WSL2 на NVMe. Начальный бюджет одного Odoo-стека ориентировочно 3–5 ГБ RAM Odoo, 1–2 ГБ БД, менее 0,25 ГБ MQTT, 0,5–1 ГБ генератор; это ориентиры, RSS измерить, одинаковые лимиты заморозить.

SimPy/Python: старт **6 процессов**, измерить 4/6/8 на одинаковых тяжёлых и лёгких входах, выбрать по реальному throughput/RSS. До импорта NumPy установить `OMP_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1`, `MKL_NUM_THREADS=1`, `NUMEXPR_NUM_THREADS=1`. Для B допустимы два идентичных, полностью изолированных Odoo+PostgreSQL+MQTT окружения только после бенчмарка. Для C — один стенд и 20 реально активных пользовательских сессий; тяжёлый SimPy в этот момент выключить. Диск держать с резервом не менее 100 ГБ свободного пространства; никакого автоматического prune.

Измерить CPU/RAM/swap/SSD во время пилота и сохранить `environment_before.json`, `environment_after.json`, `ENVIRONMENT_SETUP_RU.md`, Compose config, хеши образов, реальную версию Python и `benchmark_4_6_8.csv`. OOM, прогрессирующий swap, перегрев или дисковый дефицит — основание снизить параллельность/остановить безопасно, **не** менять исследуемые модули или сокращать количество измерений.

## A3. ЕДИНАЯ МЕТОДИКА ВРЕМЕНИ, ТРУДА И ПРОИЗВОДИТЕЛЬНОСТИ

**Основная единица — одно предложенное поступление со всеми грузовыми единицами.** Начало `t_first_ready`, конец `t_standard_close`; отдельный `T72=min(t_close-t_ready,72ч)` с флагом закрытия. Открытые/альтернативные случаи не исчезают из расчёта, доля успеха показывается отдельно. Между сравниваемыми масками для (S,L,seed) идентичные входящие `case_id`, состав, времена готовности, повреждения и внешние события. Время ожидания порождается запросами ресурсов/внешних результатов, не назначается отдельным коэффициентом.

**Длительность операции:** для каждого реального посещения сохраняй `ready`, `resource_request`, `resource_granted`, `service_start`, `service_end`, `wait_reason`, `branch_status`. `service=service_end-service_start`, `resource_queue=grant-request`, иные ожидания отражаются отдельно. Не считать одновременно и `wait` от `ready` до `grant`, и его часть от `request` до `grant` дважды. Операции, не применимые к данному случаю, имеют `visit_count=0` и явную причину `NOT_APPLICABLE`.

**Человеко-минуты:** суммарное занятое время всех назначенных лиц по делу/поступлению, включая водителя, ОТК, производственный персонал, проверку и переключения. Очередь поступления без занятости человека не считается трудом. Обед и короткие перерывы уменьшают доступную мощность, но не становятся трудозатратами конкретного поступления. Процент занятой мощности = `busy_time / practical_available_time` для каждой роли; платить по штатному фонду и расходовать активные минуты — разные показатели.

**Машино-минуты:** реальные физические рейсы и обработка; `active`, `reserved`, `idle`, количество рейсов, пустой и гружёный пробег. Физическая работа не сокращается из-за скорости HTTP. P10/P18 резервирует связку «водитель+погрузчик» на время рейса; если возникла реальная очередь по одному из ресурсов, не держать второй ресурс бесконечно без соответствующего учёта, избежать deadlock. Для P19 машину можно держать в резерве, но движение не учитывать повторно.

**TO-BE:** до первого основного run создать `operation_transition_registry.csv` на 25 операций: исходное ручное поддействие, сохранённая часть проверки и движения, изменённая частью модуля, автоматическая система и измеренная/сценарная задержка, ошибки/отказы/резервная работа. Не назначать произвольные −10/−30%; значение каждого эффекта — результат событийного исполнения.

**Сквозная причинность:** длительности параллельных действий не суммировать для получения T72. Для полного потока сформировать DAG события→ресурс→последовательность и вычислять причинный критический путь, включая внешнее ожидание, с тестом `sum(critical_path_contributions)+residual=T_case` для завершённых. В отчёте показывать вклад B1–B5 и P01–P25, а не только итог C000/C127.

**Экономика:** отдельно показанные `human_minutes`, `equipment_active/reserved_minutes`, `queue_minutes`, сменная мощность, затраты на ошибки и интеграции. TDABC: единая тарифная ставка × использованное время; если стоимость погрузчика указана с водителем, не прибавлять зарплату водителя дважды. Экономия рабочего времени ≠ автоматическое сокращение ФОТ. Происхождение цен и CAPEX/OPEX сценарное, если подтверждений площадки нет.

## A4. НЕИЗМЕНЯЕМОЕ ЖУРНАЛИРОВАНИЕ: КАЖДЫЙ RUN, КАЖДЫЙ CASE, ВСЕ 25 ШАГОВ

Выполни как обязательное условие приемки результатов:

- `runs.parquet`: все 46 080 идентификаторов запусков, включая ошибки и PARTIAL, входные манифесты, mask, S, L, seed, версия кода, SHA256 параметров, число поступлений, состояние аудита.
- `cases.parquet`: **каждое предложенное поступление каждого запуска** с `case_id`, `t_first_ready`, `t_standard_close`, `t_obs_end`, `T72`, outcome, числом паллет, общим человеком/техникой; по P01–P25 — *визиты, активное время, очередь по причинам, занятость людей/водителей, время машины active/reserved, состояние ветви, first_ready и last_service_end*, по B1–B5 —  показатели на каждом блоке и вклад в критический путь. Запрещено сохранять только среднее по seed или конфигурации.
- `resources.parquet`: одна строка на фактический интервал учёта ресурсов, роли, практическая мощность, занятость, перерывы, простои и очередь.
- `operation_aggregate.parquet` и `comparisons_by_operation.csv`: по каждому `(scenario,load,seed,mask,operation)` число применимых случаев, количество визитов, среднее и распределение активного времени/очереди, человеко-минуты и машино-минуты на всё предложенное поступление, доля пропуска ветви. **Не делить только на завершённые случаи**.
- `diagnostic_operation_visits.parquet`: все реальные визиты для заранее зафиксированной выборки случаев, для всех нарушений и тяжёлых хвостов.
- `case_replay_tool.py`: команда `--run-id --case-id --trace` воспроизводит конкретный прогон и точную историю указанного поступления, проверяет хеш входа/кода/параметров и равенство вектора 25 этапов сохранённому `cases.parquet`; формирует читаемую таблицу `P01..P25`, события, ресурс/длительность/ожидание и критический путь. Проверить на 10 предзаданных случаях C000/C127 и S4/S6. Если полной детерминированности нет — блокировать основную серию до исправления либо сохранять полные визиты для каждого поступления.

Пиши сжатые Parquet по `scenario/load/seed/config`, атомарно; после каждого блока сохраняй checkpoint. Сохрани manifest хешей всех результатов. Подробные JSON всех внутренних событий не требуются, если полный replay доказан. При недоказанной реконструкции нельзя утверждать, что события полностью доступны.

**Читаемый обязательный отчёт после каждого законченного блока сравнений:** таблица 25 операций `C000 / Cxxx`: число посещений и пропусков, активное время одного визита, очередь одного визита, активные и человеческие/машинные минуты на предложенное поступление, вклад в критический путь, разница в минутах, проценты (с NA при нулевой базе), ссылки на run/case-ledger. Отдельно свод B1–B5 и общий T72 с долей успешных/открытых. Готовый шаблон — `examples/STAGE_COMPARISON_TEMPLATE.csv`.

## A5. ЭКСПЛУАТАЦИОННАЯ ОПТИМИЗАЦИЯ БЕЗ СНИЖЕНИЯ ОХВАТА

- **Вычисление A:** один раз фиксируй внешние входы `(S,L,seed)` и предоставляй их всем 128 маскам, но внутри симуляции у каждой маски отдельное mutable состояние. Общее случайное число для неизменяемых поддействий должно зависеть от логического идентификатора действия, а не порядка вызовов RNG, иначе корреляции сломаются от параллельности.
- Профилируй `{C000,C063,C127} × {S1/L1,S4/L2,S6/L3}` на технических seeds с `4/6/8` процессами, затем заморозь выбор и оптимизируй I/O/кэш, а не бизнес-время. Предпочтительно 6 processes на i5-14400F, 8 — только при реально лучшей скорости и отсутствии swap. Не сохраняй внутренние события в stdout.
- **Интеграция B:** ускоренный событийный маршрут, но настоящие записи в Odoo, реальные проверки полномочий и транзакций, всё без 440-секундных ожиданий. При 2 изолированных стэках БД, брокер, порты и тома не пересекаются; любой сброс данных воспроизводим и подтверждён.
- **Стресс C:** 25 масок strength-3, каждая проходит S1–S6/L1–L3 и три seeds с 20 реально работающими пользователями. На одном стенде поочерёдно, окна 60+15 секунд. 1 350 × 75 секунд = **28 ч 7 мин 30 с** минимум, так что за ночь весь C может не завершиться. Остановки/resume не меняют научный протокол.
- Для всех отдельных TO-BE масок не добавлять рабочих, погрузчики, площадь, новые источники будущих данных и изменения лабораторной методики. Бизнес-скорость отдельного случая определяется текущими ограничениями и очередями, а не желаемым коэффициентом.

| P24 | B5 | Передать обязательные результаты и проверить завершение обмена | Подтверждён обязательный обмен без повторного оприходования |
| P25 | B5 | Зафиксировать исход обработки поступления | Стандартный успех, открытое исключение либо уполномоченный иной исход |

Маршрут не является 25 безусловными ручными задачами на каждую паллету. Реализуй ветвления, условные исправления, общие документы на поступление, общий объект качества и параллельное обслуживание паллет. Не выписывай акт брака при отсутствии брака.

Шаги качества и регистрации согласуй в едином state machine. Наличие физического груза, заблокированного учётного количества, разрешения качества и финального размещения — разные состояния. Допустимое временное движение должно иметь учётное основание; оно не создаёт второй приход после разрешения. Одинаковая логика качества обязательна во всех масках.

Определение основной границы:
- case_id = документ поступления с неизменным согласованным составом паллет;
- для каждой паллеты задано внешнее время готовности; состав документа зафиксирован до выбора конфигурации;
- `t0_case` = готовность первой предназначенной к данному поступлению грузовой единицы; остальные времена готовности сохраняются. Разницу до готовности последней паллеты показывай как внешнее формирование поступления, не приписывай её WMS;
- `t25_case` = стандартный успешный исход после обработки всего состава, необходимых решений и обязательного подтверждения данных;
- перемещение только первой паллеты, приёмка под удержанием и отправка сообщения без подтверждения не являются t25;
- иные разрешённые исходы учитываются отдельно. Нельзя “ускорить” процесс отказом принять трудные случаи;
- периодический сменный отчёт существует отдельно. В P23–P24 входят только обязательные итоги данного поступления. Не добавляй искусственно ожидание конца суток ко всем случаям;
- в каждом варианте все 25 функций представлены событиями. Функция может исполняться автоматически, использовать ранее полученный результат или иметь ветку `NOT_APPLICABLE(reason)`, но не исчезать из проверки результата.

## 4. Семь модулей: строго ограниченные области изменения

| Модуль | Состояние 0 | Состояние 1 |
|---|---|---|
| M1 Производство–WMS | Сотрудник передаёт/подтверждает сведения о поступлении штатным способом | Событийная доставка основания, состава и его версий; подтверждение обработки и очередь ошибок |
| M2 Качество–WMS | Сотрудник получает и связывает уполномоченное решение с продукцией | Надёжная автоматическая доставка и применение того же решения по объекту качества |
| M3 Сквозной workflow | Раздельные действия ввода, проверки, оформления и закрытия | Повторное использование уже доступных сведений, автоматические проверки/документы и контролируемое закрытие |
| M4 Адресация и задания | Безопасное штатное правило выбора допустимого места и назначения | Прозрачное улучшенное ранжирование допустимых мест/задач, резервирование и назначения |
| M5 IoT прибытия | Инициируемое человеком считывание ТСД | Стационарное считывание и обнаружение прибытия; исключения и резерв остаются на ТСД |
| M6 IoT состояния зоны | Оценка физической зоны по доставленным штатным событиям | Дополнительные измерения входа/выхода и занятости с проверкой актуальности, используемые в управлении |
| M7 ML | Простой фиксированный прогноз по доступным планам/истории | Локальная обучаемая модель по тем же разрешённым источникам; не меняет алгоритм действий сама по себе |

Все 7 переключателей логически независимы. Минимальные интерфейсы, корректный учёт, роли, журнал и проверка безопасности — ОБЩАЯ ИНФРАСТРУКТУРА, присутствующая в каждой конфигурации. Она не должна бесплатно включать функции M1–M7.

Обязательные правила сочетания:
- M1=1, M3=0: сведения пришли автоматически, но штатные отдельные подтверждения остались.
- M3=1, M1=0: переиспользуются только реально полученные/введённые данные. Автоматика не знает недоставленных документов.
- M2 не сокращает длительность лабораторной методики и не создаёт раннее разрешение. Меняются только доставка, связывание и работа участника по передаче.
- M5 не отменяет проверку состава и качества. Считывание идентификатора не равно успешной приёмке.
- M6 работает и без M5: счётчик присутствия может измерять число объектов, но не выдумывает их идентификаторы. Идентичность получают только допустимым каналом.
- M4 должен работать без IoT и ML; использует доступное штатное состояние.
- M7 должен работать без IoT: использует доставленные события ТСД и доступную информацию. Не создавай техническую зависимость “ML возможен только с M5/M6”.
- Включение M7 не включает скрыто M4. Прогноз передаётся через один общий интерфейс. Набор допустимых действий и правило применения прогноза при сравнении M7=0/1 остаются одинаковыми.
- Если без M4 политика не имеет полезного действия для прогноза в конкретном состоянии, фиксируй отсутствие изменения. Это допустимый нулевой операционный эффект, а не повод удалить комбинацию или добавить тайное действие.
- Для всех автоматизаций реализуй отказ, повтор, восстановление и ручное исключение. Их время и стоимость входят в результат.

Не присваивай одному и тому же уменьшению ручного ввода одновременно эффект M1, M3 и M5. Эффекты определяются сравнением полных запусков; пересечение функций выявляется взаимодействиями модулей.

## 5. Комбинаторика и три НЕСМЕШИВАЕМЫХ контура V3.1

Полная факторная схема сохраняется: семь независимых бинарных модулей M1–M7, C000–C127, все S1–S6 и L1–L3. Не удаляй маски по результатам пилота. Для каждого сравнения используется один и тот же case manifest, начальный запас, физические и информационные ограничения, набор событий и критерий закрытия.

**A. PROCESS_SIMULATION — ОСНОВНАЯ НАУЧНАЯ СЕРИЯ.**
128 масок × 6 сценариев × 3 нагрузки × 20 повторов (seeds 3000–3019) = **46 080 ускоренных процессных запусков**. Единица — полное поступление P01–P25; физическое время, 72-часовой индивидуальный горизонт наблюдения, труд, техника, бизнес-эффект. Этот контур НЕ СОКРАЩАТЬ. V3 пилоты seeds 2900–2902 не являются результатом основной серии. Запуски можно пакетировать и параллелить независимыми процессами при неизменном seed/экзогенном вводе. Не смешивать разные версии кода в одной серии.

**B. LIVE_ODOO_CONTRACT — ВСЕ СОЧЕТАНИЯ, БЕЗ ФИКСИРОВАННОГО ОЖИДАНИЯ 440 С.**
128 масок × 6 сценариев × 3 нагрузки × 3 повтора (seeds 4000–4002) = **6 912 событийных интеграционно-транзакционных replay на настоящей Odoo 19**. В каждом replay существуют 20 независимо авторизованных пользовательских сессий с неизменным набором ролей; проверяются реальные записи, действия, MQTT, повторные сообщения, конкурентные резервы, ограничения качества, полный маршрут P01–P25 и обязательное закрытие или корректно открытый исход.

Здесь не имитируй 180 секунд нагрузочного интервала, 60 секунд прогрева и 180 секунд хвоста. Вместо ожидания запускай очередное действие в тот момент, когда выполнены его фактические зависимости. Сохранение порядка длительных *бизнес*-событий обеспечивай общей виртуальной шкалой входных событий с явно доставленными решениями, НЕ ожиданием лабораторных суток в wall time. Реальные сетевые/API-задержки измеряются отдельно в wall-clock и не используются для сокращения физических минут процесса. Не разрешай переход до фактической записи/подтверждения. Прогон заканчивается, когда для всех тестовых case есть проверенный стандартный/альтернативный/открытый исход с указанной причиной. Деактивированные модули не получают информацию из будущего.

Количество поступлений, состав, сценарные дефекты и расписание событий фиксируй до запуска и делай одинаковым для всех масок одного (S,L,seed). L1/L2/L3 различаются исходным предложенным объёмом 1/1.5/3, а не результативностью варианта. Реальная активность всех 20 сессий одновременно не гарантируется размером входной когорты: сохраняй реальные пиковые одновременные запросы и отдельно выполняй обязательную конкурентную гонку как минимум 20 параллельных авторизованных запросов с проверкой доменной целостности. Это **контрактный replay, не длительный 20-пользовательский стресс**.

**C. LIVE_ODOO_STRESS — ПРОДОЛЖИТЕЛЬНАЯ НАГРУЗКА, ЧЕСТНАЯ СТРАТИФИКАЦИЯ.**
Используй **25 масок, предопределённых в `STRESS_MASKS_25.json`**: 16-масочный covering array strength 3 для семи бинарных модулей плюс девять контрольных масок из прямых гипотез (одиночные эффекты, M4+M6, C063/C127). Это не отбор лучших результатов по таблице.

Обязательный список 25 масок (десятичный номер Cxxx; приоритетное отображение ML — в конце):
`C000, C001, C002, C004, C008, C014, C016, C023, C025, C032, C037, C040, C043, C050, C060, C063, C064, C067, C077, C084, C090, C102, C104, C113, C127`.
Для математической проверки покрытия используй семь ненулевых четырёхбитных столбцов с общей первой координатой 1:
`1000, 1100, 1010, 1001, 1110, 1101, 1011`. Для всех `u=0…15` значение бита j равно `parity(u & column[j])`; получатся 16 OA-масок. Добавь предзарегистрированные `C001,C002,C004,C008,C016,C032,C040,C063,C064`. Выполни unit-тест: для любых трёх модулей встречаются все восемь комбинаций 0/1; размер итогового объединения равен 25.

Для КАЖДОЙ выбранной маски проведи ВСЕ S1–S6, L1–L3, три повтора (seeds 5000–5002), постоянный состав 20 пользователей. Это **25 × 6 × 3 × 3 = 1 350 реальных нагрузочных окон**. Действительные временные показатели live вычисляются только из этого контура.

В каждом нагрузочном окне одинаковая реальная длительность основной фазы: **60 секунд** (не менее, даже если предложенная работа уже завершена), после — **15 секунд** фиксации хвоста и остатка. Аутентифицируй и прогрей постоянные 20 сессий и Odoo до начала блоков измерений, НЕ по 20+60 секунд заново перед каждой маской. До каждой маски обязательно корректно сбрось бизнес-состояние/очереди/брокер и проверь чистоту данных. Если сброс обнуляет сессии/кеш, восстанови одинаковое состояние до начала измерения; не подменяй холодный старт прогретым только для улучшенных масок.

Доставляй открытым генератором **одинаковую заранее запланированную бизнес-нагрузку** всем маскам одного (S,L,seed) независимо от скорости HTTP-ответов. Используй точно 20 клиентских сессий с фиксированными ролями. Задачи производству, складу, качеству, исполнителям и закрытию исполняются по зависимостям; технические сервисы отдельно. Поступление не ускоряется “полученным заранее” решением качества. L1=1×, L2=1.5×, L3=3× от одной замороженной входной интенсивности, выбранной по preflight C000 без поиска выгодного для IoT/ML режима. Метрические показания о хвосте через 15 секунд — отдельно от полной сквозной длительности в SimPy.

В 60-секундной фазе фиксируй как минимум offered/accepted/closed/open, p50/p95/p99 HTTP по типам записи, latency ожидания клиента и очереди, CPU/RAM/DB, 20-пользовательские конфликты, ошибки повторной доставки, фактическую долю операций, завершённых при ограниченном wall-clock. Если в заданной нагрузке слишком мало образцов для содержательного p95, пометь метрику `INSUFFICIENT_SAMPLES`, не дописывай фиктивные запросы и не округляй как успех. Для сильных заявлений о долговременном SLA требуются отдельные длинные контрольные окна — не превращай краткий stress в доказательство 24/7.

Не выдавай strength-3 покрытие 25 масок за все 128 длительных стресс-тестов. Четырёхсторонние и более сложные аппаратные взаимодействия в live-стрессе остаются непокрытыми. Полные взаимодействия 128 модулей оцениваются в A; корректность всех масок/сценариев/нагрузок проверяется в B.

Статусы и обязательные поля: `PROCESS_SIMULATION_COMPLETE`, `LIVE_CONTRACT_COMPLETE`, `LIVE_STRESS_SELECTED_COMPLETE`, `LIVE_STRESS_FULL_FACTORIAL_NOT_RUN`; указать эти статусы явно. Сводный статус `COMPLETE_REFERENCE_V3_1` возможен при полном A+B+C и указанном ограничении C. Ни один статус не имеет смысла “6912 полных непрерывных 440-секундных тестов”.

Порядок запуска: preflight → аудит прежнего пилота → заморозка методики V3.1 → A+B (можно в безопасной последовательности/разных средах) → C → независимый аудит → аналитика. Код и input hashes фиксируй до каждой основной серии. Любой ранее помеченный INVALID_FOR_COMPARISON пилот не включай в статистику.

**Производительность A — отдельный обязательный preflight без потери полноты:** после фиксации корректности 25-операционного процесса измерь реальную скорость выполнения и число событий на как минимум трёх предзаданных технических контрастах (C000/C063/C127 на S1/L1, S4/L2 и S6/L3) с пометкой PILOT_ONLY. Оцени медиану и хвост времени одного запуска, объём памяти, размер аудита и суммарный вычислительный бюджет для всех 46 080 по реальным профилям. Используй кэширование НЕМЕНЯЮЩИХСЯ экзогенных входных manifest на (scenario, load, seed); модель F1 обучай один раз на зафиксированной обучающей части, а не заново для каждого запуска; рассчитай статические координаты/совместимость один раз на сценарий. Разрешается CPU-параллелизм SimPy по независимым процессам и пакетный вывод Parquet. Не выводи полные подробные JSONL каждого события в каждом запуске, если тот же независимый потоковый аудитор проверяет инварианты во время исполнения, сохраняет контрольные суммы и доступен точный повтор по seed/code/input hash. Детальные трассы храни для предзарегистрированных контрольных, ошибочных и крайних случаев. Если детального журнала нет — не заявляй повторный независимый событийный аудит именно по этому журналу. Запрещено ради скорости снижать интенсивность потока, число паллет, число реплик, долю исключений или менять результаты.

Если оценка полного A остаётся несовместимой с вычислительными ресурсами, сначала оптимизируй код и запись, затем запускай resumable параллельные пакеты. Сохраняй статус PARTIAL с точным остатком, но не заменяй полную статистику выборочно выполненными seeds и не обещай асинхронную доставку в будущем.

## 6. Данные, сценарии, нагрузки, персонал

Сначала проверь локальные исходные данные и их лицензию. Используй имеющийся внешний поток операций и одинаковый источник всех вариантов. Если данных нет, попробуй восстановить их из зафиксированного источника проекта. Не подменяй их молча другим набором.

У исходного потока могут отсутствовать реальные документы, партии качества и этапы информационной обработки. В этом случае создай один явно синтетический слой поступлений, документов и качества ДО испытаний, не называя его данными предприятия.

В `input_contract.json` зафиксируй:
- правила связывания case_id / production_lot_id / quality_case_id / pallet_id / sku;
- фактические времена готовности и физического поступления, версии планов и моменты их доступности;
- правило группировки паллет в поступления: использовать исходный документ, если он есть; иначе фиксированную группировку по товару/источнику/временному окну и ограничению размера с явной меткой ASSUMPTION;
- распределение размеров поступлений, их готовности и длительности формирования; без ручной группировки под результаты;
- независимые очереди участников, транспорт, складские места, доступность зон и внешние выбытия;
- параметры деятельности вне логистики: объективный результат и длительность качества, готовность документов и продукции. Их нельзя ускорять модулем, который меняет лишь связь.

Базовый AS-IS не ухудшай искусственно: не отключай уже имеющиеся проверки, не добавляй обязательные повторные согласования и не ставь таймер ожидания только затем, чтобы автоматизация его сняла. Ручная операция должна иметь назначение и вход/выход. Новые ручные операции не назначай нулевыми из-за отсутствия данных. Для каждой составь `parameter_registry.csv`: значение/распределение, единица, объект “на поступление/паллету/исключение”, происхождение, диапазон неопределённости, принадлежность ресурсу.

Порядок выбора: фактическое доступное измерение → явно применимый прежний профиль → отдельно объявленное новое сценарное допущение. Не объявляй серверный runtime временем работника. Не переносить 9 часов очереди из Business Studio как фиксированный sleep. Очереди возникают из расписаний, входов, служебных действий и ограниченных ресурсов.

Если для новых операций данных нет, самостоятельно подготовь центральный исследовательский профиль из конкретных действий (открытие, проверка полей, ввод, подтверждение, передача), укажи длительности и допущения до пилота. В итогах обязательно REFERENCE_ONLY. Нельзя “вычислить” продолжительности из желаемых процентов экономии. Пилот разрешает исправление технической реализуемости, не поиск наиболее выгодных входов.

Физическую модель используй общую для всех масок. Унаследованные числа (например, 5 329 мест, два погрузчика, профиль ручного считывания) являются сценарными, а не подтверждёнными характеристиками действующего предприятия. Новые роли производства/ОТК/закрытия должны иметь явные ресурсы и календари, не бесконечное обслуживание.

S1 — штатные условия.
S2 — повреждённые/нечитаемые идентификаторы и ошибки/недостаток сведений. У всех вариантов одинаковые исходные дефекты; способы обнаружения и исправления могут различаться.
S3 — сбои передачи, дубли, задержки и восстановление. Задай физически определённые каналы; одинаковый сбой общего канала действует на все использующие его маски. IoT не получает иммунитет, штатный ТСД не отключается произвольно.
S4 — ограниченный приёмочный буфер. Один размер буфера и одна физическая ёмкость для всех масок в сценарии.
S5 — ограничения хранения, заполненность и удержание качества. Сохраняй заданную совместимость товара/зоны и карантин; специальные места допускаются только как явно обоснованный сценарный профиль, не `row_id % 5` и не специально подобранные ближайшие места.
S6 — неравномерный вход/пики и возможное расхождение плана с фактом. Сохраняй одинаковое суммарное число входящих объектов для сравниваемых масок, меняй профиль пика только на уровне сценария.

За основу значений сбоев можно взять замороженный протокол V1, но все изменения, необходимые полному процессу, отдельно перечисли и зафиксируй. Не меняй scenario_id, сохранив под ним другую физическую постановку без пояснения.

Нагрузки: L1 = 1,0×, L2 = 1,5×, L3 = 3,0× одного источника. Старые номинальные 300/450/900 паллет/сутки — только ориентиры. Показывай фактические паллеты И поступления в сутки. Способ изменения потока одинаков для всех масок; внешнее освобождение мест не подстраивается под успешность алгоритма.

Все маски одного (scenario, load, seed) получают идентичные экзогенные входы, начальный запас, карту, персонал, технику, готовность продукции, качество и потенциальные внешние сбои. Возникшие очереди/назначения/ошибки нового оборудования не обязаны совпадать: это результаты модели.

Случайность адресуй ключом (seed, entity_id, operation_id, attempt_id, source). Не используй один последовательный RNG, порядок которого меняется от включения модуля. Хеш экзогенного входа должен совпасть у всех 128 масок в парном блоке. Полный заранее созданный manifest/ground truth принадлежит генератору и оценщику. Политики и интерфейсы WMS видят только свой доставленный срез состояния; наличие полного manifest в тестовой фикстуре не означает, что все его поля заранее известны оператору или ML. Добавь тесты нарушения этой границы доступа.

## 7. Исполнение, горизонт и незавершённые случаи

Для PROCESS_SIMULATION:
- 1 сутки прогрева;
- 30 суток включения поступлений в основную когорту по t0_case;
- ещё 3 суток наблюдения;
- на протяжении донаблюдения сохраняй заранее заданный фоновый поток/выбытия и нагрузки. Не превращай конец кампании в искусственно пустой склад;
- каждое поступление основной когорты наблюдается ровно до своего t0_case + 72 часа для первичного сравнения. Последняя включённая запись должна получить весь горизонт.

Первичный показатель времени:
`T72_i = min(T_success_i, 72 часа)`.
Если стандартный успех не достигнут за 72 часа, включая отвергнутые/ограниченные исходы, T72=72 часа; исход показывается отдельно. Это наблюдаемое ограниченное среднее времени до СТАНДАРТНОГО успеха, а не обычное среднее всех окончательных циклов. Оно не позволяет выиграть за счёт отказа от сложных поступлений.

Одновременно сообщай:
- фактический цикл каждого завершённого поступления;
- среднее среди завершённых с явной пометкой selection/censoring, НЕ как главный итог;
- доли стандартного успеха за 2/4/8/24/72 часа (исследовательские пороги, не SLA СИБУра);
- долю и возраст открытых, удержанных и альтернативно закрытых случаев;
- остаток на конец основного окна и на единый 72-часовой горизонт по каждому case;
- квантили по полной когорте: если нужный процент не завершился за 72 часа, писать “не достигнут / >72 ч”, а не вычислять P95 только по быстрым завершившимся.

Дальнейшее наблюдение полного завершения допустимо как одинаковый дополнительный слой для ВСЕХ масок, но не заменяет первичный горизонт и не стирает перегрузку.

Для LIVE_ODOO используются wall-clock метрики и свой одинаковый тестовый горизонт. Его результаты не пересчитывать в физические часы склада. Часы модели и компьютера хранятся в разных полях и никогда не складываются.

## 8. Метрики полного процесса и блоков

Главный объект: одно поступление с фиксированным составом. В каждой таблице отдельно подписывай единицу и уровень агрегации.

Обязательные показатели:
1. T72 полного процесса, мин/поступление.
2. Фактическое время стандартного закрытия завершённых случаев и число цензурированных.
3. Человеко-минуты на то же поступление: все роли, работа с документами, сканирование, проверки, исправления, закрытие.
4. Машино-минуты на то же поступление: пустой ход, гружёный ход, установка, разрешённые повторные перемещения.
5. Полные ресурсные затраты по этому поступлению и отдельно расходы ИТ/модулей.
6. Стандартно завершённый объём, альтернативные исходы и незавершённая работа.
7. Число ручных действий, повторного ввода, исключений, повторных обработок и ошибок.
8. Полнота/задержка событий, свежесть показаний, доля fallback и вмешательств человека.
9. Пробег, ожидающие задачи, доступные совместимые места, занятость ресурсов и буфера.
10. Качество прогноза и доля решений, реально изменённых благодаря прогнозу/наблюдению.

Месячные человеко-часы и машино-часы — отдельные показатели мощности. Не сравнивай их на одной шкале с минутами цикла. Не дели календарные затраты всей смены на случайно выбранное число быстро завершившихся паллет.

Блоки неизменны: B1=P01–P05; B2=P06–P11; B3=P12–P16; B4=P17–P21; B5=P22–P25.

Для каждого блока и каждой Pxx храни: вход, первый/последний выход, применимость, число посещений, автоматическое/ручное исполнение, активное человеко- и машиновремя, ожидание, причина, loop_id, результат. При повторе считай фактическую дополнительную работу, не только первый проход.

Различай:
- активное время ресурса;
- время жизни операции/блока;
- задержку сообщения;
- ожидание ресурса;
- время, когда несколько ограничений действуют одновременно.

Не складывай перекрывающиеся времена параллельных паллет и проверок в “полный цикл”. Для аддитивного объяснения сформируй критический путь фактического экземпляра или взаимоисключающую временную разметку. Её сумма должна совпасть с наблюдаемым полным циклом/горизонтом. Обычные средние длительности блоков показывай отдельно с предупреждением о перекрытиях. Не выдавай диагноз причины за название стадии.

По причинам ожидания сохраняй все активные блокировки и одну явно заданную приоритетную причину для неперекрывающейся сводки: документы, регистрация, физический допуск в буфер, качество, допустимое место, ресурс, решение диспетчера, подтверждение, закрытие. “Полный буфер” — состояние, не доказанная конечная причина; дополнительно проверяй, почему его нельзя освободить.

## 9. ML и использование прогноза

Одна прогнозная задача: число готовых к поступлению паллет на следующие 30 минут по допустимым группам зон. При наличии реальных планов — оценка отклонения от ДОСТУПНОГО плана. Не создавать точный производственный план из будущего тестового потока.

F0: фиксированный простой прогноз по доставленной истории и законно доступному плану. F1: одна локальная модель (по умолчанию Ridge(alpha=10); иную модель допустимо выбрать только до фиксации протокола). Обе получают одинаково доступную информацию в паре масок, отличающихся только M7.

Хронологический train/validation/test. Обучение и настройка только до основной серии, без данных seeds 3000–3019/4000–4002. Внутри теста входные лаги обновляются только доставленными событиями. Не изменять модель по результатам контрольных прогонов. Если исходный holdout короче 34 модельных суток, не дополняй его обучающими днями. Используй заранее зафиксированный блочный replay/ресэмплинг только тестовых периодов с одинаковыми входами для масок, документируй повторение исходных дней и границы блоков; такой поток является производным сценарным рядом, не 34 новыми независимыми днями наблюдения. При разных наборах доступных признаков фиксируй общий pipeline и соответствующие обученные артефакты по информационному профилю; все обучаются на одной обучающей истории, не на своих тестовых ответах.

Алгоритм использования прогноза реализуй отдельно и заранее. Предпочтение — понятная оценка ближайших допустимых действий по прогнозной нагрузке/ожиданию в тех же временных единицах, а не произвольный балл за ожидаемую паллету. В наборе действий должны быть “сохранить текущий план/ничего не переставлять”, существующие допустимые задания и, только если предусмотрено, перемещение свободной техники с полной стоимостью пробега и времени.

При включении M7 не добавляются люди, места, техника, разрешения качества или бесплатные подготовительные операции. При отсутствии полезного действия фиксируется отсутствие воздействия.

Для малого ПРЕДОПРЕДЕЛЁННОГО диагностического набора можно подключить идеальный прогноз и переставленный прогноз. Это дополнительные проверки механизма, не 128-я новая архитектура и не часть оценок практического ML. Их результаты не использовать для повторной настройки по тесту. Если идеальный прогноз не помогает, это диагностический результат, не повод переделывать тест до победы ML.

## 10. Реальная доработка Odoo, ТСД и интеграций

Используй существующую зафиксированную Odoo Community 19 и PostgreSQL, Docker Compose, устанавливаемый модуль/сервис `wms_research_v3`, MQTT/Mosquitto, Python и scikit-learn. Сохрани старый стенд. Зафиксируй фактические версии и image digests; не требуй платных Enterprise-компонентов и внешних SaaS.

Реализуй новые функции В ПРИЛОЖЕНИИ, а не только в SimPy:
- поступление, manifest, производственные/качественные связи, состояния 25 операций;
- переключатели M1–M7 и аудит их работы;
- мобильный веб-интерфейс ТСД: поступление, идентификация, исключение, задание, адрес, подтверждение;
- производственный адаптер и адаптер качества с версиями и подтверждениями;
- приём IoT-событий через шлюз; дедупликация, outbox/inbox, ретраи и сверка;
- выбор/резервирование допустимого адреса и назначение задачи на ПОЛНОЙ тестовой карте;
- настоящее исполнение изменений через штатную складскую бизнес-логику Odoo;
- полный состав поступления и подтверждаемое информационное закрытие.

Логику принятия решений вынеси в общую библиотеку, используемую симулятором и приложением, с адаптерами доступных состояний. Нельзя передать Odoo только заранее выигравший адрес. В тесте она/сервис должны выбрать его из нескольких конкурирующих адресов, а затем исполнить операцию.

Не изменять stock-остатки прямым SQL и не подменять ORM-проводки собственной таблицей. Не предполагай названия полей старых версий: проверь модели в фактически запущенной 19.0. Для связанного назначения/резервирования обеспечь атомарность и повторяемость. Несколько HTTP-вызовов сами по себе не образуют единую транзакцию.

Роли и полномочия реальны: оператор ТСД не может снять качество. Технические учётные записи интеграций имеют минимальные права, а не универсальное `sudo`. Секреты в `.env`, в артефактах только шаблон. Приложение слушает локальную/изолированную сеть; никаких изменений производственных систем.

Тесты MQTT — с настоящим брокером. Минимальный общий адаптер доступен каждой конфигурации для корректного исполнения, но модуль OFF не должен сам выполнять заявленную автоматизацию.

M6: различай событие изменения и heartbeat/периодический снимок. Одинаковое значение с новым подтверждением не устарело. Недостоверный снимок не становится фактом. Fallback использует оценку той же ФИЗИЧЕСКОЙ величины, а не количество всех незакрытых задач. Все чтения ground truth разрешены только эмулятору устройства и независимому оценщику.

## 11. Ускоренное настоящее Odoo: метод выполнения B и C без фиктивной экономии времени

### 11.1. Общие ресурсы, роли и честная граница времени

Odoo Community 19, PostgreSQL, `wms_research_v3`, HTTP/ТСД, Mosquitto/MQTT, реальные проводки и конкурентное резервирование. Одинаковая конфигурация Odoo, физические ресурсы, схемы, роли и версии кода в каждой паре. Одно приложение не является эквивалентом SAP EWM.

**20 пользователей во всех live-проверках:** 2 производство; 6 складские операторы; 4 исполнители перемещения; 2 качество; 2 диспетчеры; 2 закрытие/учёт; 2 руководитель/контроль. Пользовательские сессии отличай от IoT/интеграционных service accounts. В быстром контрактном replay проверяй существование этих 20 сессий и состязательные операции; не изображай постоянную загрузку всех 20, если они не получили работу. В длительном C поддерживай 20 готовых клиентов и фиксируй реально активные.

Есть ТРИ разные временные шкалы: (i) model time реального складского процесса в SimPy; (ii) logical event time контрактного Odoo replay; (iii) wall time сервера/HTTP/технической нагрузки. Полный цикл `t25-t0` по поступлению и 72-часовой контроль — главная метрика только (i). Логическое ускорение событий в (ii) не означает измерения физического времени (i). Задержка HTTP (iii) не заменяет сменные операции людей.

### 11.2. Событийный контрактный replay B (6 912)

- Из одного замороженного `case_manifest` воспроизведи полный P01–P25 со всеми ветками документов/качества/приёмки/резервирования/перемещения/закрытия. Каждый case содержит 2 или больше паллет по зафиксированному правилу — не сокращать сложные документы до одного SKU при критической ветке.
- Для одного (S,L,seed) все 128 масок получают те же документы, объекты и дефекты. Никаких sleeps с длительностью 20/60/180/180 секунд. Применимое качество становится доступным только после предусмотренного логического события и по защищённому API полномочий. Длинный hold моделируй последовательностью событий и реальным ограничением статуса, а не ожиданием суток в HTTP.
- У каждой тестовой маски сбрасывай бизнес-записи, остатки, задания, ключи идемпотентности, очередь доставки и контролируемые брокер-состояния к общему snapshot. Сохраняй стабильность инфраструктуры; проверяй по хешу стартовый запас и все 20 учётных записей. Можно реализовать быстрый `seed/cleanup` тестовой области вместо полного восстановления SQL-снимка, но только при доказанной идентичности постусловий, отсутствии утечек и корректном invalidation caches. Нельзя просто вычистить таблицу остатков в обход проводок и назвать это штатной работой WMS.
- Стартуй бизнес-задачи при готовности предусловий, не используй фиксированный таймер на завершение. Если ожидаемое событие не придёт, зафиксируй открытое состояние и связанное логическое событие истечения предельного горизонта. Неразрешённое качество не может получить искусственное разрешение ради завершения кейса.
- Выполни конкурентные проверки: два оператора подтверждают одно поступление; резервирование одного адреса разными пользователями; повтор MQTT-event; конфликт устаревшей версии документа; одновременное закрытие с одной неразмещённой паллетой. Там, где возможно, синхронизируй 20 авторизованных запросов барьером, но показатели latency транзакции сравнивай только при одинаковой форме нагрузки.
- Передаётся фактическая работа через API Odoo; нельзя подтверждать адрес, выбранный только SimPy и заранее предоставленный в Odoo единственным кандидатом. Алгоритм и контроль ограничений должны работать в Odoo-модуле или сервисе.
- Заверши replay сразу после проверки предусмотренных исходов всех cases и аудита. Сохрани длительность исполнения, но НЕ выдавай её за 60- или 180-секундную устойчивую пропускную способность.
- Никаких 440 секунд в таймере каждого replay. Если исполнение занимает слишком долго, профилируй реальные вызовы/пересоздание БД/сложные документы. Не сокращай case cohort ради скорости.

### 11.3. Устойчивый краткий стресс C (1 350)

- При единственном хосте запускай только одно нагрузочное окно одновременно, чтобы не искажать throughput и CPU; не параллель реальные live-стрессы на общей машине. Параллелить можно только ускоренный SimPy.
- Сначала подними сервер и 20 сессий, проведи общий технический прогрев/проверку кеша. Затем запускай блоки, восстанавливая один и тот же набор бизнес-данных после каждого окна, с контролем очищенного состояния. Рандомизируй порядок масок внутри S/L блока по заранее зафиксированному seed, повторяй C000 по графику как контроль дрейфа производительности, но эти дополнительные калибровочные окна не подмешивай к факторным результатам.
- Для каждого окна предзапланируй 60 секунд поступлений и 15 секунд фиксированного хвоста. Ни недостаточное число отправленных кейсов, ни неответивший сервер не сокращают знаменатель offered. Открытый генератор не должен замедлять подачу из-за медленного варианта. Сохраняй свой логическая/календарная время, состояние, очереди и незавершённую работу.
- L1, L2, L3 реализуй как 1×, 1,5×, 3× входную интенсивность, а не как изменение числа пользователей. Во всех окнах 20 клиентских сессий и одинаковое распределение ролей; число запросов может отличаться при автоматизации — это измеряемый результат. Зафиксируй `offered`, `service_requests`, `user_actions`, `completed`, `open`, `failed`, `service_latency`, `client_queue_latency`, `cpu`, `db_locks`.
- S3 содержит реальные детерминированные сбои MQTT и сетевого адаптера внутри 60 секунд, а не только приписанные failure flags. S5 проверяет HOLD и разрешённый карантин, не ждёт физические сутки; эти ветки логически ускоряются, и результаты не являются производственным временем выполнения качества.
- Следи за прогревом и остатком незавершённой работы; перед серией зафиксируй правило стартовой очереди. После первых блоков не изменяй 60+15 сек по наблюдаемому эффекту. При превышении ресурсов фиксируй FAILED/OVERLOADED, а не пропускай тяжёлые конфигурации.
- 3 повтора подают тот же профиль нагрузки и имеют собственные seed 5000–5002. Трёх повторов недостаточно для узкого ДИ очень высоких квантилей: считай метрики наблюдательными, сохраняй их реальную неопределённость и никакого автоматического утверждения о промышленном SLA.

## 12. Проверяемость и независимый аудит

Обязательные инварианты для каждого запуска:
- единый состав поступления и однозначные связи документов/партий/паллет;
- не более одной успешной первоначальной приёмки одной грузовой единицы по основанию;
- нет чужого/повторного резерва, недопустимого адреса и переполнения физической ёмкости;
- временная перевозка и карантин учитываются, но не снимают качество;
- только применимое уполномоченное решение изменяет качество;
- нет отрицательных остатков после проведённого движения;
- физический баланс согласован с местами, транзитом и буфером; учётное и физическое состояния не обязаны совпадать при допустимой задержке;
- закрытие не происходит до обязательных результатов всего состава;
- недоставленные документы/решения и будущие события недоступны политике/ML;
- одновременные действия 20 пользователей не создают двойных проводок.

Аудитор — отдельный обработчик реальных событий, не вызов той же функции `is_valid()`, которую проверяет. Поля нулевых нарушений заполняются только после проверки с указанным охватом.

Прогони контрольные мутации: двойной приход, чужая ячейка, неразрешённое качество, повторное списание, раннее закрытие при одной неразмещённой паллете, потерянное подтверждение, устаревшая версия документа, гонка двух резервов. Рядом корректные отрицательные контроли: повтор сообщения с одной проводкой, разрешённое карантинное размещение, отказ по отсутствующему запасу без изменения количества.

Сохраняй события с occurrence_time, receive_time, processing_time, case_id, pallet_id, lot_id, operation_id, actor/role, correlation_id, event_id, causation_id, document_version, состояние до/после и решением. Для качества — ссылка на источник/разрешение. Одного имени события `external_release` недостаточно для аудита прав в Odoo.

Для всех запусков выполняй потоковую независимую проверку и сохраняй первичные данные case/pallet/operation. Полные события храни сжатыми чанками либо обеспечь точное воспроизведение по зафиксированным входам и проверяемым хешам чанков. Факт независимого полного пересчёта и авторская потоковая проверка — разные поля. Отчёт не должен расширять фактический охват.

Проверь повторяемость выбранного до запуска набора seeds/масок. Порядок масок в live рандомизируй по блокам для уменьшения влияния прогрева машины; набор входов от этого не меняется. Параллелить ускоренные симуляции допустимо. Live-сравнения на одной машине не запускай конкурентно друг с другом.

## 13. Статистика, одиночные эффекты и взаимодействия

До основных прогонов зафиксируй следующие первичные проверки. Все измерения проходят ПОЛНЫЙ процесс, а не один этап:
H1: M1 против AS-IS, S1/L2 — уменьшение T72 поступления.
H2: M2 против AS-IS, S5/L2 — уменьшение T72 при неизменной внешней методике качества.
H3: M3 против AS-IS, S1/L2 — уменьшение общей трудоёмкости на поступление.
H4: M4 против AS-IS, S4/L2 — уменьшение T72.
H5: M5 против AS-IS, S1/L1 — уменьшение общей трудоёмкости на поступление.
H6: M4+M6 против M4, S4/L2 — уменьшение T72 именно от использования наблюдения.
H7: все семь модулей против M1–M6, S6/L2 — добавочное уменьшение T72 от ML.

Это новые проверки, не переименование прежней H2. До анализа сформируй `hypotheses.json` с нулевыми/альтернативными гипотезами, контрольной маской, метрикой, единицей и условиями.

Парная единица — целый повтор с общим экзогенным потоком. Не считать тысячи паллет независимыми повторениями. Bootstrap 5000 перевыборок целых seed, seed_bootstrap=20261119, интервалы 95%. Для первичной семьи H1–H7 дополнительно рассчитай корректные парные p-values и Holm при alpha=0.05; исходный и скорректированный результат сохраняй. Одного непоправленного интервала недостаточно для общей декларации всех семи эффектов.

Практический ориентир: 5% улучшения первичной метрики. Это критерий проекта, не норматив отрасли. Различай: статистически различимо; практически достигает порога; неопределённо. Для сильного заявления о практической пользе нижняя граница улучшения должна превышать 5%, а не только точечная оценка.

Защитные условия: ноль проверенных нарушений; доля стандартного успеха за 72 ч не ухудшается более чем на 0,5 процентного пункта по соответствующей односторонней проверке; нет роста неучтённых отказов; стоимость и ресурсная нагрузка показаны. Это не “доказанная безопасность” при неполных логах.

Остальные сравнения — разведочные. Для больших семейств показывай FDR/BH q=0.05 с явным семейством; не выдавай случайно лучший из 127 вариантов за заранее подтверждённую гипотезу. Победителя без независимой проверки называй лучшим в данной серии, не промышленным оптимумом.

Обязательно рассчитай:
1. Каждую маску против C000 внутри одного S/L/контура.
2. Полный набор модулей против остальных масок по тем же условиям.
3. Каждый модуль на всех фонах остальных шести: пары c и c+Mi. 64 фона на модуль. Покажи, где добавление полезно, вредно или не влияет.
4. Парные взаимодействия всех 21 пар модулей на одинаковых фонах. Для меньшего времени синергия `I = mu_i + mu_j - mu_0 - mu_ij`. Положительное I означает выигрыш сверх суммы отдельных улучшений; единицы — минуты. Для каждого фона используются соответствующие четыре маски.
5. Тройки, четвёрки и т.д. — их фактические полные эффекты, а не сумма процентов одиночных модулей. Полное насыщенное высокопорядковое объяснение не нужно объявлять причинным доказательством без мощности.
6. Прямые взаимодействия M1×M3, M2×M3, M4×M6, M4×M7, M5×M3 вынеси в понятные бизнес-объяснения.

Процент в таблицах:
`change_pct = 100 * (mean_variant - mean_control) / mean_control`.
Для меньшего показателя отрицательное изменение благоприятно.
Отдельно `improvement_pct = 100 * (mean_control - mean_variant) / mean_control`.
Используй отношение средних по повторам, не незаметную смесь со средним индивидуальных процентов. Интервал процентов получай из парного bootstrap. Если контроль равен нулю, процент NA с пояснением; абсолютную разницу сохраняй. Для долей отдельно процентные пункты.

Сопоставляй одинаковые case cohorts и показывай разрез по размерам поступления/маршрутам. Не улучшай удельную стоимость исключением тяжёлых незавершённых случаев.

## 14. Бизнес-эффект без фиктивной экономии

Для каждой маски отдельно:
- изменение полного цикла;
- изменение активной работы всех ролей;
- изменение работы техники, включая новые/повторные движения;
- объём завершения и долговременный остаток;
- расходы обработки ошибок и ручного резерва;
- дополнительные инфраструктура, устройства, интеграции и сопровождение.

Не монетизируй ожидание паллеты по зарплате работника. Время погрузчика с водителем не дублируется отдельной оплатой того же водителя. Высвобождение рабочего времени не равно уменьшению платежей. Ускорение лабораторного решения, предотвращённый брак, кражи, внешнее хранение и рост продаж не начисляются без соответствующего измеренного механизма.

Покажи ресурсную стоимость на ОДИНАКОВУЮ входящую когорту и показатели завершённости. Стоимость на завершённое поступление — дополнительно; все затраты незавершённых отображаются, не исчезают.

Создай модульную смету с общими и повторно используемыми компонентами. Общий шлюз/сервер/адаптер считается один раз, не семь раз. Если сметы неизвестны, не выдавай выдуманные суммы за цены. Рассчитай допустимый бюджет/порог OPEX по измеренному ресурсному эффекту и явным сценариям монетизации.

В отдельном FINANCIAL_SCENARIO допускаются прежние ориентиры ставок 650 руб./ч оператора и 1200 руб./ч погрузчика с водителем, 5 лет, ставка дисконтирования 20%, монетизация 0/25/50%. Они не фактические тарифы предприятия. Историческую стоимость лицензий Loginom не назначай локальному ML автоматически.

Формула сценарного NPV: `-CAPEX + sum((monetized_benefit_y - incremental_OPEX_y)/(1+r)^y)`.
Объём года и освоение явно задаются; не повторяй бесконечную перегрузку как устойчивую годовую работу. Для неустойчивого потока с растущей очередью отметь, что прямое годовое масштабирование невалидно; рассчитай недостающую мощность/открытый объём, а NPV не выдумывай. Недостающие входы должны порождать объяснение и пороговый расчёт, а не молчаливую пустую таблицу.

- Фактическая реализация нового выбора адреса и заданий В Odoo; нельзя заранее подсунуть единственную ячейку, выбранную SimPy.
- Отчёт корректно разделяет TIME_SIMULATION, CONTRACT_REPLAY и WALL_CLOCK_STRESS и не выдаёт их за хронометраж предприятия.
- Честная оценка эффекта IoT, обычных WMS-правил и ML; отрицательные/нулевые эффекты сохраняются; экономика основана на заданных сценарных ценах, без вымышленного промышленного ROI.

Это НЕ статус "6 912 непрерывных 440-секундных окон Odoo". Техническое требование такого старого плана заменено на B+C, потому что 6 912 фиксированных окон на одном последовательном хосте требуют 35 суток чистого wall-clock. Число 6 912 сохранено как полное реальное функционально-интеграционное покрытие Odoo, длительные стресс-окна выполняются для заранее заданных 25 масок. Это обоснованная смена дизайна тестирования, не буквальное сохранение прежнего нагрузочного охвата.

Если завершено только A+B, статус `PROCESS_AND_CONTRACT_COMPLETE__STRESS_PARTIAL`; если только часть — `PARTIAL` с точными счётчиками, manifest оставшихся и командой resume. Если окружение недоступно — `BLOCKED`. Исправления ошибок после заморозки требуют новой версии кода/протокола и перезапуска всех затронутых сравнений, с явной маркировкой ранних пилотов INVALID_FOR_COMPARISON.

Итоговая рекомендация должна сравнивать Pareto-кандидатов по T72, труду, технике, закрытию, ошибкам и сценарным затратам. Не выбирать победителя по одной наименьшей цифре с 128 вариантов без контроля множественности и отдельной проверки. Ответь на пять вопросов:
(1) что даёт обычная интеграция WMS;
(2) что дают IoT-прибытие и наблюдение зоны сверх WMS;
(3) где полезен/не полезен локальный ML;
(4) какие комбинации дублируют друг друга или ухудшают результат;
(5) какие ограничения физические и автоматизацией не снимаются.

Успех — воспроизводимый сквозной эксперимент и честный уровень доказательности, а не обязательная победа IoT/ML или формальная галочка полного стресс-теста.

# ПРИЛОЖЕНИЕ II: МЕТОДИКА И АУДИТ ИЗМЕРЕНИЙ

# V3.2 — заморозка AS-IS и методика измерения (дополнение к V3.1)

## Статус
**Предрегистрационная предлагаемая конфигурация.** Это не данные промышленного склада и не результат нового запуска. Пользователь пока не запускал основную V3. Нельзя продолжать старые пилоты как будто они рассчитаны в этой параметризации.

Числа в `ASIS_BASELINE_PARAMETER_FREEZE.json` — единая исходная исследовательская гипотеза для всех 128 масок. Они намеренно детализируют реальную ручную работу человека вместо малых таймеров нажатия кнопок. Выбор отдельных значений ещё требует профессиональной проверки или заводского хронометража; их нельзя называть верифицированными.

## Почему не задаём итоговую длительность
`T_case = t_standard_close - t_first_ready`. Нельзя назначить 90 или 120 минут на входе. Полное время возникает из расписания поступления, обслуживания, ограничений, конкуренции за персонал и технику, внешних решений и подтверждений.

`C000` — WMS + ручные ТСД, без складского IoT, без упрощённого workflow и ML. `C127` не получает отдельные коэффициенты ускорения; М1–М7 изменяют действия и доступные события.

## Консервативное повышение базовой трудоёмкости
Новая базовая таблица: 25 операций, распределения `triangular(0.7×mode, mode, 1.3×mode)` на конкретное исполняемое действие, а не на весь процесс. P10/P18 используют неизменённую физическую формулу расстояний и обработки.

При **только иллюстративной** структуре 1 937 поступлений и 7 680 паллет из предыдущего технического пилота, без очередей, переключений, перерывов и усталости, сумма новых центральных ручных операций ≈20,84 чел.-мин/поступление; водитель на P10/P18 ≈20,39 чел.-мин/поступление; итого **≈41,24 чел.-мин/поступление**. Это не среднее сквозное время и не замер V3.2.

## Измерение в обоих вариантах

1. **Полный цикл:** от первого t_ready до подтверждённого стандартного закрытия ВСЕГО поступления. Отдельно T72=min(T_success,72h) для неуспешных/открытых. Отдельно доля закрытых, число неуспешных, времена только завершённых (без представления как всей генеральной совокупности).
2. **Активный труд:** за каждый реально занятый ресурс списывать `end_busy-start_busy`. Водитель погрузчика — человек; его минуты учитываются как труд. Два человека по минуте — 2 человеко-минуты, а не 1 минута цикла. Время ожидания задания без занятия работника трудом не является.
3. **Использование техники:** время работы погрузчика, занятость/резервирование погрузчика, пробег и обслуживание раздельно. Физическая длительность хода не сокращается только из-за программной автоматизации.
4. **Занятость человека:** `busy / scheduled_available`, учитывая смены, перерывы, и переработку. Отдельно сохранять `paid_capacity`, `available_capacity`, `idle_time`, `break_time` — не переводить автоматически сэкономленные рабочие минуты в зарплатный ФОТ.
5. **Очереди:** SimPy `resource.request` → `grant`, и ожидания других причин. На человека и станок нет бесконечной мощности. Время очереди по операции не является временем работы сотрудника.
6. **TO-BE:** заменить ТОЛЬКО исходные поддействия. Сократилась передача/перенос данных — проверка факта и права подписи остаются. В P02 физическая проверка остаётся при M5. Решение качества и лабораторная методика сохраняются во всех масках. У M4/M6/M7 преимущества могут появиться только от иных решений и очередей, не от «скорости 30%».
7. **Экономика:** TDABC: цена практической минуты ресурса × использованные минуты + фиксированная/переменная IT-стоимость. Ставка погрузчика `с водителем` не может применяться одновременно с отдельной полной ставкой водителя без вычитания одного из компонентов.
8. **Устойчивость:** заранее провести чувствительность к общим неопределённым параметрам, не подстраивая параметры под результаты. При изменении registry обновить version/hash, заново запускать все маски и держать старую серию отдельно.

## Человеческий фактор

- Разброс длительности на каждом исполнении, **общий случайный базовый квантиль по одинаковому действию во всех масках**.
- Ограниченные рабочие ресурсы, работа по сменам, два коротких перерыва по 10 минут и обед 30 минут за смену с разнесением по сотрудникам.
- Переключение контекста: 8 секунд при реальной смене типа задания/поступления одним работником (не при любом событии), одинаково для всех конфигураций.
- При коэффициенте занятости выше 85% за предыдущие 120 минут — предварительное сценарное замедление ручных действий на 10% (не погрузчика, не лаборатории). Это не установленная психофизиологическая закономерность; предрегистирована проверка на 0/10/20%.
- Не вводить новый универсальный процент человеческих ошибок, пока он не обеспечен данными. Исходные дефекты S2, сбои S3 и качество S5 одинаковы для всех вариантов, события исправления оплачиваются временем и ресурсами.
- 20 пользователей Odoo — не штат склада. Моделируемое число работников из утверждённой карты `workers_per_shift`; менять кадровую мощность между конфигурациями запрещено.

## Сохранение доказательств

`runs.parquet` — каждая конфигурация × сценарий × нагрузка × seed.

`cases.parquet` — КАЖДОЕ предложенное поступление по каждому run, его фактический конец/неуспех/ограничение T72 и отдельные временные ряды/векторы 25 операций, чтобы можно было увидеть из чего получилось время.

`resources.parquet` — бюджеты рабочих часов, реально занятые часы, перерывы, ожидания, машины и дистанции.

`diagnostic_operation_visits.parquet` — подробные визиты для заранее выбранной репрезентативной выборки по 6 сценариям × 3 нагрузкам × 128 маскам, **всех выявленных нарушений** и тяжёлых хвостов. Для всех случаев сохраняются воспроизводимые seed, hash входов, параметров, кода и политики.

Это сохраняет точный результат каждого поступления, но не требует постоянно записывать все внутренние события SimPy в JSON. По данным пилота около 68 603 выполненных визитов на один прогон: прямое подробное сохранение всей матрицы было бы порядка 3,16 млрд строк; поэтому полный внутренний трейс должен включаться при воспроизведении конкретного запуска.

**Важно:** агрегированные векторы по операциям позволяют проверить суммы и метрики, но не показывают точную очередность всех повторных посещений. Для доказательства полной причинной цепочки конкретного случая нужен детальный трейс или детерминированный replay. Не приписывать агрегатам невозможную степень аудита.

2. Обновить регистратор ресурсов так, чтобы водитель погрузчика учитывался отдельно от техники; добавить оборудование `reserved` vs `active`.
3. На малом заранее зафиксированном проверочном наборе подтвердить равенство учётных сумм и воспроизводимость 2× запуска seed.
4. Пересчитать пилоты C000/C127 с новой параметризацией; СТАРЫЕ 82,34 и 78,38 минут не приводить в качестве V3.2.
5. Заморозить `ASIS_BASELINE_PARAMETER_FREEZE.json` и все контрактные файлы SHA-256 до первой основной записи. Только после этого — 46 080 запусков, 6 912 replay и 1 350 стресс-окон по правилам V3.1.

# ПРИЛОЖЕНИЕ III: РЕГЛАМЕНТ НОЧНОГО ИСПОЛНЕНИЯ

# WMS V3.1 — ночной режим исполнения на ПК i5-14400F / 32 GB / Samsung 990 Pro

## Цель

Ты работаешь в существующем проекте `wms_inbound_experiment` на Windows + WSL2 + Docker Desktop. Реализуй оптимизацию **исполнения**, не дизайна научного исследования. Сохрани протокол V3.1: 128 масок, S1–S6, L1–L3, 20 повторов, 46 080 сквозных процессных запусков; 6 912 событийных интеграционных replay Odoo; 1 350 отдельных непрерывных стресс-окон Odoo по 20 пользователей. Статус уже выполненных пилотов не меняй. Не подменяй частичные результаты полными, не смешивай модельное и реальное время.

Доступное железо: Intel Core i5-14400F (6P+4E / 16 потоков), 32 ГБ RAM, Samsung 990 Pro NVMe (1 ТБ свободно), RTX 3060 12 GB. GPU для текущего протокола не применять. Во время ночного запуска пользователь оставит ПК включённым и без лишних нагрузок. На одном хосте **не запускать одновременно независимые продолжительные стресс-окна Odoo**: они начнут конкурировать за ресурсы и изменят измеряемую производительность.

## 1. Обязательный preflight (перед основной серией)

1. Убедись, что V1/V2 и исходные V3-пилоты неизменны; зафиксируй `git status`, hashes протокола и данных, версии Python/SimPy/Odoo/Postgres.
2. Сними реальную загрузку CPU/RAM/SSD и параметры WSL/Docker; если `.wslconfig` устанавливает доступную память менее 18 GB, выдай конкретную рекомендацию, но не перезагружай WSL во время уже идущих контейнеров.
3. Измерь время и пиковую память как минимум девяти контрастов маска × сценарий/нагрузка: {C000, C063, C127} × {S1/L1, S4/L2, S6/L3}, с несколькими независимыми техническими seeds, помеченными PILOT_ONLY. Сохрани `benchmark.csv` с временем, числом событий, RSS, выводом журнала и throughput events/sec.
4. Измерь масштабирование ProcessPoolExecutor при 4/6/8 процессах на **одном и том же предзаданном** небольшом наборе задач. Выбери шесть, если восемь почти не ускоряют или вызывают swap/троттлинг. Не используй Python threads для CPU-heavy SimPy.
5. Рассчитай ETA по эмпирической смеси лёгких/тяжёлых задач. Не давай обещаний до бенчмарка. Для завершения 46 080 за 8 часов нужно в среднем не более 3,75 секунды CPU-wall на запуск при эффективных 6 параллельных исполнителях, без учёта накладных расходов.

## 2. Процессная серия A: максимально ускорить, не менять результатов

1. Сохраняются 46 080 запусков, экзогенные входы, начальные остатки, конкуренция ресурсов, 25 операций, 72-часовой исход поступления, модельные ветвления и инварианты. Ни одного пропуска комбинаций или seeds.
2. Группируй задания по `(scenario, load, seed)`: **ровно один раз** готовь immutable входной manifest для всех 128 масок. Его SHA-256 должен совпадать для всех масок внутри блока. Не предоставляй политикам будущие данные.
3. Храни manifest и неизменяемые таблицы адресации/совместимости для повторного использования; переиспользуй зафиксированную обученную ML-модель, если это соответствует исходной границе train/validation/test. Избегай повторной загрузки CSV и повторного обучения на каждой маске. Не разделяй mutable состояние симуляций между масками.
4. Выполняй блоками через 6 `multiprocessing`-процессов, при возможности увеличь до 8 только по результатам preflight. Для каждого процесса установи `OMP_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1`, `MKL_NUM_THREADS=1`, `NUMEXPR_NUM_THREADS=1` и запрети oversubscription CatBoost/scikit-learn. Крупные read-only массивы — memmap либо безопасный кэш в воркере. Размер чанка — после профилирования, по умолчанию группируй 4–16 масок одного экзогенного блока на задачу, чтобы уменьшить overhead процессов.
5. На 10–20 контрольных траекториях сравни текущую и оптимизированную реализацию: точные входные hashes, ход инвариантов, состояния, времена, численные KPI. Не принимай ускорение, изменяющее бизнес-логику или физическое время. Точность сравнения float зафиксируй в тесте, не подгоняй под неудобный результат.
6. Не записывай все подробные JSON-события каждого запуска; проверяй четыре складских ограничения потоковым аудитором прямо в ходе моделирования. Пиши компактный агрегат на **каждый** запуск + audit hash + reproducibility manifest; подробные трассы — для заранее заданных масок/пиковых комбинаций, обнаруженных аномалий и заранее зафиксированных seed. При необходимости детального независимого аудита обозначь его реальный охват.
7. Пакетно записывай результаты в Parquet/CSV после валидированных блоков; не держи гигантские таблицы в RAM. Не логируй каждую успешную операцию в stdout. Каждая запись содержит mask, S/L, seed, входные хеши, 25-операционные и сквозные KPI, статусы безопасности и версию реализации.
8. Используй `checkpoint/resume`, атомарную запись и идемпотентный re-run: завершённые блоки не пересчитываются. Составь план выполнения в перемешанном/сбалансированном порядке по S/L и маскам, не так, чтобы к утру в отчёте остались лишь лёгкие сценарии.
9. После каждого пакета проверяй `run_count`, уникальность ключей, отсутствие утечек будущей информации и баланс остатков. При сбое не маскируй invalid run.

## 3. Контур B: настоящая Odoo, интеграционный replay

1. **Не выполняй B во время активного CPU-бенчмарка A**, если это ухудшает точность тестирования. Выполняй после A или при реально свободных ресурсах.
2. 6 912 повторов остаются, а fixed sleeps отсутствуют по утверждённому V3.1. Проигрывай полный 25-операционный контракт событийно и обязательно проверяй транзакции, качество, приёмку, документы и закрытие.
3. Для безопасного ускорения разрешены два изолированных Odoo+PostgreSQL стека с разными портами, базами, очередями и data volumes. Выбирай 1 vs 2 по практическому benchmark (RSS/throughput/error), а не автоматически запускай 2. Оба стека используют одну и ту же зафиксированную версию, одинаковый набор данных, и одинаковые лимиты ресурсов.
4. Каждый replay начинает с одного и того же начального состояния; снапшот или откат должен исключать наследование остатков и историй от предыдущей маски. Убедись, что в каждой проверке есть действительно одновременные действия 20 пользователей в предусмотренных критических точках, а не просто 20 авторизованных сессий.
5. Отчёт по B касается корректности транзакций и API latency во время replay, **не** 60-секундного стресс-режима.

## 4. Контур C: непрерывная нагрузка Odoo

1. Исходный V3.1 — 25 masks × 6 S × 3 L × 3 повторов = 1350 окон; 60 секунд активного теста + 15 секунд хвоста = **28 ч 7 мин 30 с** чистой длительности. **Объективно не поместится в одну 8–10-часовую ночь на одном изолированном стенде.** Не обещай обратного и не ускоряй реальное время с помощью SimPy.
2. Для этой ночи C выполняй **только после A и B при наличии оставшегося бюджета**. Сохраняй полный план на последующие сеансы с детерминированным resume. Запуски C выполняй отдельно, без тяжелых A/B, чтобы задержки не зависели от фоновых вычислений.
3. Чередуй маски, S/L и seeds предзаданным сбалансированным порядком, не делай подряд только C000/S1/L1. Сохраняй все timestamps, P50/P95/P99 API, throughput реальных проводок, ошибки, активных клиентов и обратное восстановление.
4. Запрещено называть частичную C-серию проверкой всех 1350 окон. Если пользователь решит отдельно сократить C, оформи как **новый протокол с меньшим статистическим покрытием**, не молча.

## 5. Порядок выполнения на одну ночь

- Бюджет ориентировочно 8–10 часов, пользовательский ПК останется включенным. Не рассчитывай его по системному времени без учёта возможного сна/паузы; предотвращай sleep средствами ОС только с разрешёнными пользовательскими настройками.
- Фаза 0: audit + 9 контрастов + 4/6/8 workers benchmark, freeze implementation.
- Фаза 1: **максимум ночного времени — на полную серию A**; 6 (или по проверке 8) процессов; checkpoint каждые 1–5 минут либо после завершения небольшой группы; автоматическое восстановление.
- Фаза 2: если A закончена — серия B с 1 или 2 изолированными стеками.
- Фаза 3: если A и B закончены — начать C с исходным стабильным протоколом, сохранять прогресс.
- Если A по benchmark заведомо не поместится за ночь, не снижай число 20 повторов, 128 конфигураций, 6/3 условия. Просто запускай те же пакеты с checkpoint/resume и утром предоставь точное покрытие.
- Не выполняй idle sleep в цикле опроса завершения рабочих задач. Не разрешай одновременное переполнение RAM и swap.
- При достижении лимита температуры/троттлинга или резком росте RAM автоматически уменьшай число воркеров и помечай конфигурацию измерений; при перегреве/ошибках безопасно останови пакет и сохрани checkpoint.

Создай `experiment_v3/report/NIGHT_EXECUTION_REPORT_RU.md`:
