# Ночной запуск V3.2

Основная модельная серия A запущена 20 ноября в 01:19 по Москве. Текущий подтверждённый счётчик и активный блок доступны в checkpoint.json. На каждого предложенного участника процесса с единицей учёта «поступление» записываются идентификатор, состав, времена, исход и 25 пооперационных значений каждого показателя, включая труд, технику, очереди и вклад в критический путь. Прогрев и фон отмечены отдельно от основной когорты.

Перед стартом прошли 22 технических запуска и отдельный тест трёх уровней параллельности. В девяти повторённых запусках все строки поступлений и сохранённые диагностические визиты совпали с первым исполнением. В replay_verification.csv перечислены 90 контрольных выборок. Для первого основного задания C000/S1/L1/3000 дополнительно проверен экспорт из рабочего тома. В нём 2 206 предложенных поступлений, 1 955 относятся к основной когорте. Во всех строках по 25 позиций, максимальная невязка разложения T72 равна 0 мс.

Грубая оценка длительности A по измеренной пропускной способности - около 39 часов при составе задач как в тесте 4/6/8. Это экстраполяция восьми заданий на 46 080, без гарантии срока и без контуров B/C. Тяжёлые S6/L3 заняли примерно вдвое больше времени, чем S1/L1. Режим непрерывного стресса C требует ещё 28 ч 7 мин 30 с на сами окна, сверх подготовки стенда.

Исполнитель сохраняет подтверждённые разделы атомарно, с SHA-256 каждого файла. Очередь и состояния заданий сохраняются в SQLite. Исключение отдельного задания получает свой статус. При возобновлении используются тот же том результатов и тот же том с зафиксированным кодом. Штатная команда из experiment_v3/v3_2 - pwsh -File resume.ps1.

После завершения A отдельный процесс на Windows начинает квалификацию реального Odoo, затем выполняет B по доступным сценариям и последовательные окна C. Допуск B/C проверяется отдельно. Пока чисел эффективности или покрытия из этих контуров нет. При закрытии приложения и перезапуске системы доступность исполнителей зависит от Docker Desktop и запуска команды продолжения. Числа в этом документе относятся к моменту запуска; контрольные файлы coverage и checkpoint содержат актуальное состояние.
