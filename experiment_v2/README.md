# WMS V2

Начните с [аналитического отчёта](writing/V2_ANALYTICAL_REPORT_RU.md) или [раздела для статьи](writing/ARTICLE_RESULTS_V2_RU.md). [Протокол](protocol.md) и его fingerprint в results/freeze.json зафиксированы после технического пилота. В [журнале изменений](CHANGELOG_V1_V2.md) перечислены исходные ограничения.

## Повтор запуска в имеющемся проекте

Из этой папки выполните `pwsh -File run_all.ps1` в PowerShell 7 с запущенным Docker Desktop и локальным Python 3.11+ для проверки исходных файлов. Оставьте папку рядом с series_py312 и h2_audit внутри wms_inbound_experiment. Используется сохранённый Docker-образ исследовательской среды из V1, указанный по идентификатору в run_all.ps1. Чтение замороженной серии защищено монтированием только для чтения. Команда проверяет fingerprint и использует завершённые атомарно записанные строки. Для выделенного живого стенда нужны исходный compose.yaml, установленные Odoo/PostgreSQL/Mosquitto и локальная конфигурация доступа, описанная в родительском README. Флаги -RepeatIntegration и -RepeatBenchmark повторяют проверки на новых тестовых приходах. Восстановление связи проверяется только у шлюза выделенного проекта.

## Где искать числа

- results/runs_v2.csv содержит 1080 основных запусков, results/ablations.csv - 400 дополнительных запусков. Парные сравнения включая абляции сведены в results/paired_effects.csv. Во всех колонках difference используется база минус сравниваемый вариант. Для своевременности и количества завершений больший показатель предпочтителен.
- results/bottleneck_diagnostic.csv содержит длительности в секундах на паллету основной когорты: primary складываются в полный цикл, active пересекаются. До регистрации последовательно выделяются буфер и регистрация. После регистрации приоритет имеют дефицит места при удержании, отсутствие обычного адреса, занятость обеих машин, затем диспетчеризация. Физическое обслуживание включает холостой подход, гружёный ход и обработку. Если при удержании доступен карантин, само удержание не блокирует первичное размещение. Итоговые причины локализуют стадию ожидания, а не доказывают эффект изменения мощности.
- results/traces содержит подробные журналы, назначения и исходы действий по контрольному seed. В actions.parquet исход действия задаётся временем окончания физического рейса, origin=-1 соответствует буферу. Пары time и empty_m при скорости 1 м/с позволяют восстановить момент физического подбора. Во время холостого подхода паллета ещё занимает буфер.
- Для каждой основной детальной трассы сохранены два ряда занятости в buffer_states.parquet и пример reason_example.csv. Для любого ID из её pallets.parquet точные интервалы причин можно получить командой внутри среды `python src/inspect_wait.py --run S4-L2-2000-B2 --pallet ID`, подставив номер. Разные причины могут действовать одновременно. capture_at может предшествовать buffer_at.
- results/occupancy_decisions.csv содержит теневую проверку решений на всех основных запусках. Оценщик сравнивает порог заполнения с физическим счётчиком, не исполняя альтернативное решение. Эта доля характеризует изменение выбора вследствие расхождения в наблюдении. Недопустимое движение проверяется отдельно.
- results/forecast_comparison.csv - ошибка прогноза, изменения назначения, сбои и переход на резерв. data/holdout.csv - оценка на исходном хронологическом ряду. Предсказательные эксперименты не используют график производства.
- results/economics.csv - сценарные чувствительности. Календарь активных часов и число размещений на конец основного окна согласованы. Задачи, начавшиеся в прогреве, могут расходовать ресурс в основном окне. Расчёт на одинаковый объём через удельную стоимость является экстраполяцией.
- results/safety_audit.json, verification.json и v1_integrity.json - проверка переходов, повторяемости и хешей V1. results/odoo_replay.json и odoo_recovery.json относятся к реальному ПО. results/api_benchmark/status.json измеряет HTTP на этом хосте.
- results/pilot и results/jobs содержат первичные записи по запускам; results/freeze.json фиксирует программную версию. charts сохраняются в figures.

P90/P95 в runs_v2.csv рассчитаны для ожидания с индивидуальным правым цензурированием по общему концу наблюдения. Это нижние границы квантилей полного ожидания. Поля unfinished_stop и unfinished_end различают остаток до и после суток донаблюдения. У доли своевременности горизонт 4 часа полностью наблюдаем для каждой паллеты основной когорты.
